Extending OmaRGB

Work starts as a GitHub issue, described in CONTRIBUTE.md. This page is the shape of the change itself. Setup for the engines that already ship is on Engines.

An OpenRGB device

A controller the OpenRGB server reports, when it can take a colour, is painted with no row. More than one per-LED colour is a gradient. A keyboard matrix runs across the keys, or down them when the panel says so, and a strip with no matrix follows the LED list. One LED, or a static mode, is one colour. Plug it in, leave the OpenRGB server running, and omargb plan should name it.

A USB id on OpenLinkHub's list is painted by that service, from share/openlinkhub.toml, unless the same controller can take a colour per LED. A database row still wins when a device should use another engine.

A database row

Named devices live in share/devices.toml. One block is the whole change when an engine already exists.

[[device]]
bus = "usb"
id = "1532:0099"
name = "Razer Basilisk V3"
engine = "openrgb"
openrgb = "Basilisk V3"
effect = "gradient"
FieldMeaning
bususb, pci, dmi, openrgb, or hass
idvendor:product in lowercase hex, a DMI vendor:name, an OpenRGB name, or a Home Assistant entity id. Shell wildcards are allowed on DMI, OpenRGB, and Home Assistant ids
enginevanguard_k08, openrgb, openlinkhub, asus_rog, framework16, or homeassistant
effectsolid for one stop, gradient for the theme stops. OpenRGB only spreads a gradient when the live device has a per-LED mode and more than one LED
openrgbName substring, when that engine has to find the device inside OpenRGB
fallbackEngine used when the first one reports it cannot run

USB and PCI ids come from lsusb and lspci -nn. A board with no USB lighting id is matched on board_vendor:board_name, sys_vendor:product_family, or sys_vendor:product_name from /sys/class/dmi/id. DMI matching is case-insensitive.

A new match rule gets a case in tests/test_omargb.py. omargb plan must show the device and must not write to hardware.

A new engine

An engine is a class with name and apply(theme, targets, dry_run). It lives in omargb/engines/ and is registered in omargb/engines/__init__.py. dry_run must not open the device. plan is a dry run.

Return a short status line. If the line contains unavailable, rejected, missing, failed, or not ready, omargb apply tries the row's fallback. not ready is also how a missing daemon asks the caller to wait.

Packages, a system service, or a udev rule go in share/painters.toml. install.sh installs them only when this machine has a device that uses the engine. source is arch or aur. An engine with no packages gets no block.

Python is 3.11 or newer, standard library only. Do not edit /usr/share/omarchy or open an Omarchy pull request for the device.

Colours

Colours come from ~/.local/state/omarchy/current/theme/colors.toml. keyboard.rgb is used only when that file has no color0 through color15. Do not sample the wallpaper, and do not invent a hue that is not in the theme file.

color0, color7, color8, and color15 are left out, and so is any slot whose strongest channel is less than 24 above its weakest. What remains has its white floor removed, and the strongest remaining channel is scaled to 255, so a pastel that looks coloured on a dark terminal does not come out as white light.

Do not mix a colour toward white. Gradient devices receive the theme stops. Other devices receive the most saturated stop. Home Assistant is the exception: the bar cycles warmest, least blue, most saturated, coolest, and brightest, and the default is warmest, so a blue stop does not win on a lamp.
